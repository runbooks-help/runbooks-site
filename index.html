Prod broke? Runbooks help.

Runbooks turns a directory of Markdown files into interactive, step-by-step operational runbooks. Files are the content, the path is the sidebar, and a ## heading is a tickable step. No database, no CMS, no authoring UI.

Built for the moment you need it

Files are the content

A runbook is Markdown with frontmatter. You edit files in your editor and commit them; the app reads a directory at runtime, so a content change needs no rebuild and no redeploy.

Steps, not walls of text

A ## heading is a numbered, tickable, collapsible step — or an unnumbered section when you want reference prose. One page can mix both.

Readable under duress

Symptom-first titles, collapsible steps, code blocks with a per-block done box, decision callouts, a rollback section, and a Zen mode that shows one step at a time.

Inputs that never leave the page

Frontmatter vars become {{TOKEN}} substitutions inside code blocks, filled in the browser — substituted client-side and never sent to the server.

Notes and a timeline

Ticking a step records a timestamped line in the notes panel. Export them, or sync them to a git repo you own.

An agent surface

Every page is raw Markdown at /<slug>.md, indexed at /llms.txt, with a full-body search API — so LLMs and scripts read the same runbooks you do.

Your knowledge, your infrastructure

Runbooks is one Go binary in a container. It reads your content/ directory, holds no database unless you turn on identity, and has no phone-home. Backups are files; content is portable Markdown.

Passkey (WebAuthn) sign-in is built in and free. It is off by default — a public runbook site needs no accounts — and when on, identity lives in SQLite, MySQL or PostgreSQL behind a small interface with no foreign keys.

Not for everyone, on purpose

Runbooks is for solo operators, small teams and game studios who keep their operational knowledge in files.

Not for you if you have a procurement team. No enterprise tier, no MSA process, no “Book a demo”.
